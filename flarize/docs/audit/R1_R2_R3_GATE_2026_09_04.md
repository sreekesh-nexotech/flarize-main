## F. Proof that ISSUED quotations use pinned renderer / template

**Design.**
- **At issue:** the server calls `getCurrentApprovedTemplatePinning()` (loader) once, adds `rendererVersion: APPROVED_TEMPLATE_VERSION` (from `src/lib/approvedTemplate.js`), and passes the object as `issueQuotation({ rendererPinning: {…} })`.
- **`issueQuotation` (workspace):** runs `normalizeRendererPinning(rendererPinning, at)` — validates every provided field is a non-empty string, defaults `pinnedAt = at`, deep-freezes; assigns to `document.rendererPinning` inside the top-level `deepFreeze({...})`. The document also carries `payload: completePayload` (frozen), `cmsPageVersions`, `commercialSnapshotId`, `bomSnapshotId`.
- **On ISSUED replay:** the server route reads `getIssuedRendererPinning(store, actor, quotationId)` → returns `document.rendererPinning`. It calls `loadPinnedApprovedTemplate(pinning)`. The loader:
  1. Resolves the file path deterministically from `name + version` (`resolveApprovedTemplatePaths`).
  2. Throws `BUNDLE_MISSING` with a message that explicitly says "Refusing to substitute another version" if that file is not on disk.
  3. Loads the bundle via generic `loadApprovedTemplate(paths)` — which already re-verifies the on-disk meta hashes.
  4. Then asserts each on-disk meta hash EQUALS the ISSUE-time pinned hash — `bundleSha256`, `templateSha256`, and (when present) `manifestSha256`. Any mismatch throws `PIN_*_SHA_MISMATCH` with the pinned vs on-disk values quoted.
- **Never a fallback.** No code path exists in the loader that substitutes a different version, a different name, or a different hash.

**Tests proving each rail:**
- v1 replay with a v2 file also on disk → still resolves v1 (test 6).
- Missing v99 bundle → `BUNDLE_MISSING`, message names "Refusing to substitute" (test 7).
- Bundle sha mismatch → `PIN_BUNDLE_SHA_MISMATCH` (test 8).
- Template sha mismatch → `PIN_TEMPLATE_SHA_MISMATCH` (test 9).
- Manifest sha mismatch → `PIN_MANIFEST_SHA_MISMATCH` (test 10).

**`rendererVersion` retention on replay:** `document.rendererPinning.rendererVersion` is frozen at issue and returned by `getIssuedRendererPinning`. Any future edit to `APPROVED_TEMPLATE_VERSION` in the renderer module does NOT affect historical documents. The renderer can compare `rendererPinning.rendererVersion` to its own `APPROVED_TEMPLATE_VERSION` and either refuse or accept — that behavior is not implemented yet (no renderer-side change was authorized), but the DATA is now available.

## G. Proof that `recommendedBadge` is frozen

**Design.**
- `resolveRecommendedBadge(packageTier, tierDisplayNames)` returns the badge string ONLY when the given tier matches `tierDisplayNames.recommendedTier`; else returns `null`. Never invents, never derives.
- `payload.system.recommendedBadge = resolveRecommendedBadge(system.packageTier, tierDisplayNames)` is computed at issue time and Object.freeze'd along with the rest of `system` — the whole payload is further deep-frozen by `buildQuotationPayload → deepFreeze`.
- On ISSUED replay `getIssuedPayload()` returns `document.payload` verbatim; no re-computation touches `tier-display-names.json` for this field.

**Tests proving each rail:**
- `badge is pinned into payload.system for the recommended tier` — value present.
- `non-recommended tier gets recommendedBadge = null (no leakage)` — no badge on premium / base rows (also inside alternatives, since alternatives are built via the same `buildQuotationPayload` path).
- `POST-ISSUE mutation of tier-display-names.json cannot change the frozen badge` — the already-built payload's `recommendedBadge` remains `"Recommended · Most Popular"` while a DRAFT rebuild with new config returns the new string.
- `missing / malformed tierDisplayNames → recommendedBadge = null (never invented)` — never fabricates.
- `recommendedBadge is a string OR null, never any other type` — schema is stable.

## I. Any unexpected scope discovered

**One scope note — server plumbing deferred, not blocking.**

`issueQuotation` now accepts `rendererPinning` as an option; when the caller passes it, it is frozen into the document; when the caller omits it, the field is `null` (legacy / DRAFT-issue path). Wiring `server-quotation.js` to actually call `getCurrentApprovedTemplatePinning()` + `APPROVED_TEMPLATE_VERSION` and pass them at every `POST /api/quotation/quotations/:id/issue` is a ONE-line addition to `server-quotation.js:265`. That file is NOT in the protected list and NOT explicitly named in the R1/R2/R3 authorization. It is also NOT strictly required to prove the contract:
- The document schema now carries `rendererPinning`.
- The loader can enforce pinning on replay.
- The reader (`getIssuedRendererPinning`) exists.

The server route can be updated in a follow-up gate alongside the other cutover wiring, without any change to the freezes done here. **No blocker.**

**Payload path note.** The R3 directive named `payload.system.value.recommendedBadge`, but the existing payload structure spreads system fields at `payload.system.*` (not wrapped in `.value`) — e.g. `payload.system.packageTier`, `payload.system.packageTierDisplayName`. The badge is pinned at the same nesting level (`payload.system.recommendedBadge`) to match the section's actual shape. Renaming `system` to be `.value`-wrapped would be a payload-shape change with wide downstream impact — explicitly out of scope. Renderer readers already walk `payload.system.*` (verified in old `quotationDocument.js` line 819 and current `approvedTemplate.js` tryTier path convention); the badge fits the same access pattern.
